# Sample synthetic match scenarios

Generated by running `node scripts/demo.js` against `test/fixtures/synthetic_movements.js`
on this branch — real output from the real code, regenerated after the
2026-09-13 second-review fix (operational feasibility split from
commercial pricing status). Every fixture is `test_data: true`; no real
bookings or PII involved.

The demo prints two views: **ingestion-order ops cards** (what a live
system would see as each booking arrives, one at a time — later bookings
in the pool aren't visible yet) and a **full-pool scan** (what a periodic
re-scan / the 7-day board sees once every booking is known). The
difference between them is itself informative — see Scenario 2.

Every match candidate now carries two independent verdicts:
`operational_feasibility` (chronology + vehicle + route relationship
only) and `commercial_pricing_status` (whether the CANDIDATE leg — the
one a SMART_MATCH/LIVE_FILL price would actually sell — has verified
route economics). None of the scenarios below wire in a
`routePriceTruthLookup`, so `commercial_pricing_status` is
`HOLD_UNKNOWN_ECONOMICS` throughout this file by construction — see
Scenario 7 and `test/economics_gate.test.js` for the cases where it
resolves `READY`.

## Scenario 1 — exact reverse leg with known duration -> operationally FEASIBLE

`SYN-0001` (`mv_syn_out_01`, known `estimated_duration_minutes: 30`)
matched **forward** in time to `SYN-0002` (`mv_syn_ret_01`, 4 days later):
`operational_feasibility: FEASIBLE`, score 95 — the clean RETURN_LOCK
candidate. (RETURN_LOCK pricing doesn't go through the SMART_MATCH
economics gate — see `src/whatsapp_cards.js#recommendedAction`.)

## Scenario 2 — the *reverse* direction of the same pair does NOT get the same answer, and that's correct

Looking at it from `SYN-0002`'s side (`mv_syn_ret_01` as the source): its
own trip duration is unknown, so matching it forward to `SYN-0001`
resolves `HOLD_UNKNOWN_TIMING` — even though the two movements are the
same exact-reverse pair. A source movement's own completion time is what
must be known to say anything chronologically, and `mv_syn_ret_01` doesn't
have that fact recorded. Directionality is not symmetric here, and it
shouldn't be silently treated as if it were.

## Scenario 3 — the SOURCE's missing economics no longer blocks operational feasibility (2026-09-13 fix)

`SYN-0003` (`mv_syn_nearby_01`) has a known duration (20 min) but no
`operator_payout`/`absolute_floor` of its own. Its best match
(`mv_syn_chain_a`, score 95, chronologically fine) is
`operational_feasibility: FEASIBLE` — under the old (buggy) design this
would have incorrectly HOLD-ed on the source's missing economics alone.
`commercial_pricing_status` still correctly reads `HOLD_UNKNOWN_ECONOMICS`
here, but for the right reason: no `route_price_truth` was supplied for
`mv_syn_chain_a` (the candidate/saleable leg), not because the source
lacks economics.

## Scenario 4 — corridor match (not exact reverse) -> operationally FEASIBLE

`SYN-0004` and `SYN-0005` both run Nadi Airport -> Coral Coast (same
direction, same corridor, not a reverse pair). `SYN-0004`'s duration (10
min) leaves enough buffer before `SYN-0005`'s pickup (50 minutes later) —
`operational_feasibility: FEASIBLE`, score 55.

## Scenario 5 — genuinely unmatched -> no candidate at all

`SYN-0006` (Suva -> Suva) has no reverse, corridor, or chain candidate
anywhere in the pool — `best match: none`.

## Scenario 6 — a chronologically-impossible reverse is INFEASIBLE, not silently dropped

`SYN-0009` (`mv_syn_chain_a`, pickup hour 20) and `mv_syn_nearby_01`
(pickup hour 3, 17 hours **earlier**) are an exact-reverse zone pair, but
`SYN-0009` cannot possibly reverse-match something that already happened
in the past relative to its own trip. Score 65,
`operational_feasibility: INFEASIBLE` — this is the P0 bug the first
2026-09-13 review caught (the old absolute-time-gap logic would have
accepted this as compatible). See `test/matcher_chronology.test.js`.

## Scenario 7 — the economics gate itself (from `test/economics_gate.test.js`, real assertions, not demo output)

Four cases, all using the same operationally-feasible exact-reverse pair,
varying only where economics are (or aren't) verified:

| Source economics | Candidate booking's own economics | `route_price_truth` for the candidate's route | `commercial_pricing_status` | `smartMatchPrice` decision |
|---|---|---|---|---|
| known | unknown | none supplied | `HOLD_UNKNOWN_ECONOMICS` | HOLD |
| known | `operator_payout` known | floor `null` | `HOLD_UNKNOWN_ECONOMICS` | HOLD |
| known | `operator_payout` null | floor known, payout `null` | `HOLD_UNKNOWN_ECONOMICS` | HOLD |
| known | none | floor **and** payout known | `READY` | OK, price = `smart_match_price` (floor-checked) |

In every row `operational_feasibility` is `FEASIBLE` — only the last row's
pricing is ever allowed through. The source having fully known economics
(first column) never once substitutes for the candidate's own
verification, in any row.

## Multi-leg chain

`SYN-0009` -> `SYN-0010` -> `SYN-0011` (Nadi Airport -> Nadi Town ->
Denarau -> Nadi Airport, same SEDAN) is discovered as a 3-leg chain by
`findMultiLegChains`, using the same completion-based forward-only check
as the general matcher for every intermediate hop — see
`test/matcher.test.js` ("multi-leg chain of 3 same-vehicle-class legs is
found").

## Known limitation carried over from the first review (still true)

In the 7-day board run (`nowIso = 2026-09-20`), `SYN-0007`'s outbound leg
falls inside the visible 7-day window but its return leg (`SYN-0008`, one
day later) falls just outside it. The board's matching pool is
intentionally limited to what's visible in the current 7-day slice — see
`docs/CEO_RELEASE_REPORT.md` item 15.
