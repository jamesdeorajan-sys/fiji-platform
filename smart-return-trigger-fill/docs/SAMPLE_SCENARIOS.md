# Sample synthetic match scenarios

Generated by running `node scripts/demo.js` against `test/fixtures/synthetic_movements.js`
on this branch — real output from the real code, regenerated after the
2026-09-13 CEO chronology fix. Every fixture is `test_data: true`; no real
bookings or PII involved.

The demo prints two views: **ingestion-order ops cards** (what a live
system would see as each booking arrives, one at a time — later bookings
in the pool aren't visible yet) and a **full-pool scan** (what a periodic
re-scan / the 7-day board sees once every booking is known). The
difference between them is itself informative — see Scenario 6.

## Scenario 1 — exact reverse leg with known duration on both sides -> FEASIBLE

`SYN-0001` (`mv_syn_out_01`, known `estimated_duration_minutes: 30`,
known payout/floor) matched **forward** in time to `SYN-0002`
(`mv_syn_ret_01`, 4 days later): `FEASIBLE`, score 95 — this is the clean
RETURN_LOCK candidate.

## Scenario 2 — the *reverse* direction of the same pair does NOT get the same answer, and that's correct

Looking at it from `SYN-0002`'s side (`mv_syn_ret_01` as the source): its
own trip duration is unknown, so matching it forward to `SYN-0001`
resolves `HOLD_UNKNOWN_TIMING`, not `FEASIBLE` — even though the two
movements are the same exact-reverse pair. This is intentional: a source
movement's own completion time is what must be known to say anything
chronologically, and `mv_syn_ret_01` doesn't have that fact recorded.
Directionality is not symmetric in this system, and it shouldn't be
silently treated as if it were.

## Scenario 3 — unknown economics, known timing -> HOLD_UNKNOWN_ECONOMICS

`SYN-0003` (`mv_syn_nearby_01`) has a known duration (20 min) but no
`operator_payout`/`absolute_floor`. Its best match (`mv_syn_chain_a`,
score 95, chronologically fine) still resolves `HOLD_UNKNOWN_ECONOMICS` —
timing being known doesn't let economics be skipped.

## Scenario 4 — corridor match (not exact reverse) with both known -> FEASIBLE

`SYN-0004` and `SYN-0005` both run Nadi Airport -> Coral Coast (same
direction, same corridor, not a reverse pair). `SYN-0004`'s duration (10
min) leaves enough buffer before `SYN-0005`'s pickup (50 minutes later) —
`FEASIBLE`, score 55.

## Scenario 5 — genuinely unmatched -> no candidate at all

`SYN-0006` (Suva -> Suva) has no reverse, corridor, or chain candidate
anywhere in the pool — `best match: none`.

## Scenario 6 — a chronologically-impossible reverse is INFEASIBLE, not silently dropped

`SYN-0009` (`mv_syn_chain_a`, pickup hour 20) and `mv_syn_nearby_01`
(pickup hour 3, 17 hours **earlier**) are an exact-reverse zone pair, but
`SYN-0009` cannot possibly reverse-match something that already happened
in the past relative to its own trip. Score 65, feasibility `INFEASIBLE`
— this is exactly the P0 bug the 2026-09-13 CEO review caught (the old
absolute-time-gap logic would have accepted this as compatible). See
`test/matcher_chronology.test.js` for the isolated regression tests
(earlier leg, identical time, overlapping time, and the literal
NAN-\>Suva/Suva-\>NAN example from the review).

## Multi-leg chain

`SYN-0009` -> `SYN-0010` -> `SYN-0011` (Nadi Airport -> Nadi Town ->
Denarau -> Nadi Airport, same SEDAN) is discovered as a 3-leg chain by
`findMultiLegChains`, using the same completion-based forward-only check
as the general matcher for every intermediate hop — see
`test/matcher.test.js` ("multi-leg chain of 3 same-vehicle-class legs is
found").

## Known limitation carried over from the first review (still true)

In the 7-day board run (`nowIso = 2026-09-20`), `SYN-0007`'s outbound leg
falls inside the visible 7-day window but its return leg (`SYN-0008`, one
day later) falls just outside it. The board's matching pool is
intentionally limited to what's visible in the current 7-day slice — see
`docs/CEO_RELEASE_REPORT.md` item 15.
