## What this round adds

1. **A hosted, HTTP-reachable synthetic-source harness** (`worker/real_booking_sync.js`'s round 17/18 design, now exercised over the network against the live preview, not just in-process). A new D1 table, `marau_synthetic_source_bookings` (migration 0030), stands in for the real `bookings` table — admin-token-gated routes let it be seeded and mutated, then `syncRealBookingEvent`/`reconcileRealBooking` are triggered against it exactly as the local test suite already does in-memory:
   - `POST /preview/admin/synthetic-source` — seed/update one synthetic source row.
   - `POST /preview/admin/synthetic-source/:ref/sync-event` — deliver an event signal.
   - `POST /preview/admin/synthetic-source/:ref/reconcile` — trigger a reconciliation pass.
   - `GET /preview/admin/synthetic-source/:ref` — inspect the synthetic source, mirror row, link, and claim state together, for verification.
2. **A real, pre-existing router bug found and fixed while building this harness**: every route in `worker.js`'s router was `return handleFoo(...)` rather than `return await handleFoo(...)`. In an async function, a promise returned (not awaited) from inside a `try` block does not route a later rejection through that `try`'s own `catch` — it propagates to the caller of `fetch()` entirely unhandled. This was a real gap in **every** route, not just the new ones; earlier rounds' fault-injection tests always called the sync module directly, never through this HTTP router, so nothing had ever exercised a genuine thrown error reaching the router's own `catch` over HTTP until this round's harness test did. Fixed by awaiting every route handler's return value — behaviourally identical when nothing throws, and now genuinely error-safe when something does.
3. **The approved staff "Review and confirm" workflow** (migration 0029, `marau_staff_review_tokens`): requesting a deal now also mints a booking-specific review token and returns a `review_link` alongside the existing (still fully mocked) WhatsApp handoff — meant to ride inside that same detailed alert, not as a separate send. `GET /preview/staff/review?token=...` renders a plain, token-authenticated staff page and **never mutates anything by itself**. Only an explicit `POST /preview/staff/review/decide {token, decision}` decides, and it does so by calling the **existing** admin handlers (`handleAdminConfirmDealRequest`/`handleAdminDeclineDealRequest`) directly — reusing existing staff functionality rather than duplicating its logic. A token is scoped to exactly one subject (one `deal_request`), expires after 24h, and grants no broader admin access (verified directly: a review token does not work against the real admin-token-gated routes).

## The 60-second confirmation promise — framing correction

The "60 seconds" figure referenced in this workflow is a **measured operational target** ops aims to hit when reviewing a real alert — not an automatic acknowledgement, not something this system enforces or verifies, and not a guarantee to the guest. ## Round 21 — corrected staff workflow: the initial transfer reservation

Codex independently verified round 19's local suite: 424/424, before round 20's P0 review-token-leak fix and this round's scope correction. **The scope correction:** the approved "Review and confirm" workflow is about the **initial transfer reservation** — the real booking landing via `real_booking_sync.js` — not (only) an additional Marau deal request. `marau_staff_review_tokens.subject_type` (migration 0031) now also covers `'booking'`. The moment a real reservation is first saved (`handleAdminSyncEvent`, `result.created === true`), a booking-scoped review token is minted and a **mock staff booking alert** (never sent for real) is returned — only to the already admin-gated caller, never the guest. Deciding a `'booking'` subject:
- requires the **same** staff authentication as every other decision (admin bearer token — never mere token possession);
- requires a **driver/vehicle already on record** on the synthetic source (`DRIVER_NOT_ASSIGNED` otherwise — mirrors the real system's own invariant and Marau's existing `handleAdminDecideBooking` rule);

- then **syncs** (`reconcileRealBooking`, reusing the exact same fresh-read/claim mechanism as every other update since round 17) so the guest's Trip reflects it.

A review token's subject is fixed at mint time and is never a client-suppliable parameter at decide time — structurally preventing a decision from ever landing on the wrong reservation (tested directly: two reservations, two tokens, one decision, only the intended one changes).

Once that one atomic write succeeds, the confirmation is done; the sync-through and the secondary audit insert are both wrapped so neither can ever surface as a top-level failure again — each is reported as its own `sync`/`audit` sub-result, explicitly distinguishing source confirmation from guest-sync completion from audit logging. A retry that lands on an already-durably-confirmed row **repairs** (re-attempts the sync, backfills a missing audit row) using the operator/timestamp **stored on the source row itself** — never the retry call's own arguments — so a retry can never re-confirm or silently substitute a different "authorised" operator.

## Round 24 — the iPhone installation blocker

James's actual iPhone test (screenshot evidence, 29 September, 9:34 AM Sydney): opening the supplied guest link in Safari correctly showed his confirmed Trip; after "Add to Home Screen", opening the installed icon showed "Create a synthetic booking" instead — the guest's own confirmed Trip was unreachable from the installed app.

**Root cause, confirmed by reading the actual client code (`worker/pages.js`):** `loadTrip()` gates the whole authenticated fetch on `getToken()` returning something first — `if (!getToken()) { showView('start'); return; }`. `getToken()`'s only two sources were `sessionStorage` and `localStorage`. The manifest's `start_url` is a fixed `"/"` (correctly, deliberately, never carrying a private token — this file is static and identical for every guest), so a standalone relaunch never has the `#tok=` fragment either. James's device demonstrated directly that the standalone home-screen container's own `localStorage` did **not** carry the token his Safari tab had just set moments earlier for the same origin — a real, previously undocumented gap this project's own existing tests never caught, because they only exercised the `getToken()` logic in isolation (assuming a populated `localStorage`), never a real device's actual storage-sharing behavior.

**Fix — genuine redundancy across mechanisms, never a single assumption:**
- **Client (`pages.js`):** a cookie (`marau_tok`) is now ALSO written whenever the token is established (from the hash), checked as an independent THIRD source in `getToken()`'s fallback chain (hash → sessionStorage → localStorage → cookie), and cleared alongside both storages on revoke.
- **Server (`worker.js`):** `requireGuestSession` now also accepts that same cookie as a second-line fallback to the ordinary `Authorization` header (`guestCookieToken`) — the identical opaque `access_token`, the identical `access_token_revoked` check, nothing about isolation/expiry/revocation semantics changes. `requireAdmin`/staff authentication (round 20's fix) is completely untouched — the cookie fallback is wired ONLY into `requireGuestSession`, verified directly by a dedicated negative test.
- **Never recovers access from a booking reference, email, or phone match** — the cookie carries the exact same already-issued token a guest already has via every other mechanism; nothing is re-derived from guest-identifying data.
- **No duplicate booking entry** — the cookie fallback only ever authenticates an *existing* session; it cannot create or substitute a new one (tested directly: authenticating via cookie then via header against the same token leaves exactly one session row).

**Test evidence:** new `test/marau_ios_standalone_storage.test.mjs` — 9/9 tests: the served script's own cookie code confirmed present, a faithful re-implementation of `getToken()` proving cookie-only recovery with both storages genuinely empty (the exact repro), cookie-only server authentication, header-precedence-over-cookie, revocation parity, invalid-cookie rejection, admin-auth non-contamination (both directions), no-duplicate-session, and a full end-to-end "reopen with only the cookie surviving" demonstration. Full suite: **247/247 engine (unaffected) + 202/202 Marau (137 pre-round-13 + 65 across rounds 17-24) = 449/449.**

> **ROUND 25 CORRECTION, recorded 2026-09-29 — the round-24 test methodology missed a real bug in the served code, and two of round 24's evidence claims overstated what was actually shown.** Codex independently reran 449/449, then executed the token/cookie functions **extracted from the real `GUEST_APP_HTML` string itself** (not a hand-copied reimplementation, which is what round 24's own new test above actually did) — and found `getCookie`'s escaping broken in the text actually served: with both storages empty and no hash, `document.cookie = 'marau_tok=test-token'` correctly returned `test-token`, but `document.cookie = 'other=1; marau_tok=test-token'` incorrectly returned `null`.
>
> **Root cause:** `getCookie` lived inside `pages.js`'s own outer `GUEST_APP_HTML` template literal as `new RegExp('(?:^|;\\s*)' + name + '=([^;]*)')`. That outer template literal silently drops an unrecognized single-backslash escape exactly like an ordinary string literal does — so the source's two backslashes (`\\s`) collapsed to one (`\s`) in the served text, and the browser's own string-literal parser then dropped that lone backslash too (`\s` is not a recognized string escape), leaving a bare `s` with zero regex meaning. The regex silently failed to match `; ` followed by whitespace whenever `marau_tok` was not the first cookie in the header. This is the same class of bug as this project's earlier "round-3 STORAGE_KEY" and "round-15 outer-scope-const" embedding lessons, via nested-escaping rather than scope-leaking.
>
> **Fix:** `getCookie` was rewritten with zero regex and zero backslashes anywhere — `document.cookie.split(';')`, `.trim()`, `.indexOf(name + '=') === 0`, `.slice(name.length + 1)` — immune to this entire bug class regardless of how many template-literal layers the code passes through. Verified directly against all four cookie-position cases (alone, before another, after another, absent).
>
> **Test methodology corrected, per explicit instruction not to rely on a copied implementation:** every client-side test in `test/marau_ios_standalone_storage.test.mjs` now extracts the real `getCookie`/`setCookie`/`clearCookie`/`getToken`/`setToken`/`clearToken` source directly out of the real `GUEST_APP_HTML` export (by locating it between fixed markers) and **executes that exact extracted text** via `new Function(...)` against a stubbed `document`/`sessionStorage`/`localStorage`/`location` — never a hand-retyped version. New tests cover both of Codex's exact cases (cookie alone; cookie after another cookie) plus cookie-before-another and cookie-absent. Full suite after the fix: **247/247 engine (unaffected) + 208/208 Marau (137 pre-round-13 + 71 across rounds 17-25) = 455/455.**
