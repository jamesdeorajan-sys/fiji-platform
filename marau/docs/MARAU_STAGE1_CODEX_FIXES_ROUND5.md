# Marau Stage 1 — fifth independent review, bounded corrections

Codex independently verified 339/339 passing tests at commit `6864edc`. This round closes three bounded findings ("MARAU — BOUNDED STAGE 1 CORRECTIONS"). No new features, no production changes, no live sends. All new roadmap ideas stay deferred.

## 1. Confirmation/reconciliation concurrency

**Finding — exact repro given:** pause immediately after a confirm attempt's `vehicle_allocations` INSERT commits but before its awaited result returns; call `reconcile-confirmation`; resume the original confirmation. Observed: reconcile returns `ROLLED_BACK_TO_REQUESTED`, the original returns `200 CONFIRMED`, and the database ends up with a `FILLED` offer, a `CONFIRMED` request, **zero** allocations and **zero** movement claims.

**Root cause:** admin authentication on the `reconcile-confirmation` call was mistaken for exclusive ownership of that *specific in-flight attempt*. It isn't — an authenticated admin can call it at any time, concurrently with a still-running confirm attempt, and the previous design had no way for the original attempt to discover that its own resources had been unwound out from under it.

**Fix — attempt-generation fencing via the `confirmation_attempts.phase` column itself:**

- Every forward-progress phase transition the confirm handler makes (`CLAIMING_MOVEMENT` → `CLAIMING_VEHICLE` → `HOLDING_OFFER` → `FILLING_OFFER` → `DONE`) is now a **CAS**: `UPDATE confirmation_attempts SET phase = <next> WHERE attempt_id = ? AND phase = <the phase THIS process last successfully wrote>`. If that affects zero rows, someone else changed the phase from under this attempt — it throws `ConfirmationFencedError` and the handler aborts **immediately, writing nothing further** (never falls back to its own `rollback()`, which would race whoever now legitimately owns the attempt).
- `reconcile-confirmation` must now **win an identical CAS** — `phase = <the phase it just read> → 'RECONCILING'` — before it is allowed to inspect or touch *any* real state. If it loses that race, the original attempt is still genuinely progressing (or finished between the read and the fence attempt); it re-reads fresh state and reports `ATTEMPT_STILL_ACTIVE` (or the actual terminal outcome) **without touching anything**.
- The confirm handler's own *self-triggered* `rollback()` (a normal business-conflict rejection, e.g. the offer got held elsewhere) also fences itself first (`phase → 'ROLLING_BACK'`) for the same reason: a normal rejection must not blindly compensate resources a concurrent reconcile call has already taken ownership of and started compensating itself.
- Two new phase values, `RECONCILING` and `ROLLING_BACK`, added via migration `0020` (SQLite can't `ALTER` a `CHECK` constraint in place, so the table is recreated with the widened constraint — the established `_new`/rename technique).
- **Verified affected-row counts everywhere this matters:** every fencing CAS, the movement-claim `INSERT OR IGNORE`, the vehicle-allocation `INSERT ... WHERE NOT EXISTS`, and the final `deal_requests` update all check `meta.changes === 1` explicitly — none of them assume success from a resolved promise alone.

**A real edge case found and fixed while implementing this:** the first version of `rollback()`'s self-fence used `phase` as the CAS "from" value unconditionally — but `phase` is still `null` when the *very first* write (`INSERT INTO confirmation_attempts`) itself never succeeded (Codex's round-4 trigger-injection scenario). `UPDATE ... WHERE phase = NULL` never matches anything in SQL (NULL is never `=` to anything), so `rollback()` was misreporting "superseded by reconcile" for a case that's actually "no row exists yet, trivially safe to compensate directly." Fixed by skipping fencing entirely when `phase` is still `null` — per the established invariant that this INSERT is the first write inside the attempt's `try` block, nothing else could have happened yet either.

**Honest scope note:** this closes the exact repro given (a pause after the vehicle-allocation commit) and every window from `CLAIMING_MOVEMENT` onward. One narrower window is **not** fully closed by this fix: a crash between the decision-claim `INSERT` (before the confirm handler's `try` block even starts) and the `confirmation_attempts` row's own `INSERT` (the first statement inside it). `reconcile-confirmation` already handles this case safely today (nothing beyond the claim could exist yet, so it just frees the claim), but a reconcile call racing *exactly* in that microscopic window could theoretically free the claim while the original then still inserts its `confirmation_attempts` row and proceeds — allowing a second, independent attempt to start concurrently. Closing this fully would need a claim-level fencing column (e.g. an `attempt_id` on `deal_decision_claims` itself, set atomically as the very first write). Not implemented here, per the bounded scope of this round; flagged for a future round if it matters.

**Tests** (`marau_codex_fixes_round5.test.mjs`): a deterministic, single-threaded reproduction of Codex's exact scenario (a test-only `__TEST_PAUSE_AFTER_ALLOCATION__` hook suspends the confirm handler right after its allocation commits, `reconcile-confirmation` is called while paused, then the original resumes) — the original now returns `409 CONFIRMATION_SUPERSEDED` and writes nothing further; the database is fully consistent (`REQUESTED`, offer `ACTIVE`, zero allocations, zero claims, claim freed); a fresh confirm then succeeds normally. A companion test proves the *opposite* case — reconcile called on an attempt that finishes before reconcile can fence it — correctly reports `ATTEMPT_STILL_ACTIVE`/`ALREADY_TERMINAL` and touches nothing. A cross-request isolation test (a rollback failure on one request never touches an unrelated request) is retained from round 4 and still passes with the new fencing in place.

## 2. Interrupted claims discoverable

**Finding:** a persisted decision claim with no `confirmation_attempts` row currently returned `ALREADY_DECIDED`, while the ops list (`GET /preview/admin/deal-requests`) reported `reconciliation_needed` for the exact same request — an internal contradiction.

**Root cause:** by the time a confirm/decline handler's own claim-`INSERT` fails, the caller has *already* confirmed (one line earlier) that `deal_requests.status` is still `'REQUESTED'` — meaning nothing has actually been decided yet, ever, in this scenario. The old code only escalated to `CONFIRMATION_INTERRUPTED` when a `confirmation_attempts` row existed and was non-terminal; if no row existed at all (an interruption before the very first audit write), it silently fell through to `ALREADY_DECIDED` — a factually wrong label.

**Fix:** whenever the claim `INSERT` fails while the request's own status is still `REQUESTED` (guaranteed at that point), the response is now **always** `CONFIRMATION_INTERRUPTED` with the actionable `recovery_action`, regardless of whether a `confirmation_attempts` row exists — a shared helper (`describeStuckClaim`/`interruptedOrAlreadyDecidedResponse`) used identically by both confirm and decline. `GET /preview/admin/deal-requests` is updated to match: any `REQUESTED` request holding an open decision claim is now flagged `reconciliation_needed: true` even with no attempt row, so the ops list and the confirm/decline gate can never disagree again.

**A pre-existing test needed updating, not silently patched:** the round-3 "concurrent confirm and decline — exactly one wins" test asserted the loser's error code was always `'ALREADY_DECIDED'`. Under the corrected semantics, the loser's exact code now legitimately depends on timing — if the winner (typically `decline`, which does far less async work) has already finished by the time the loser's claim fails, `ALREADY_DECIDED` is correct; if the winner is still mid-flight, `CONFIRMATION_INTERRUPTED` is the *more* accurate answer (nothing has actually been decided yet at that instant). The test now accepts either, with a comment explaining why — the guarantee it actually exists to prove (mutual exclusivity, final state agreeing with the true winner) is unaffected and still checked.

**Tests:** a claim inserted directly (simulating a process that died before writing even its first `confirmation_attempts` row) is reported as `CONFIRMATION_INTERRUPTED` — never `ALREADY_DECIDED` — by both confirm and decline, and is visible with `reconciliation_needed: true` on the admin list; `reconcile-confirmation` resolves it cleanly, after which a fresh confirm succeeds.

## 3. The actual change-form default

**Finding:** `pages.js` still used `active.pickup_datetime.slice(0, 16)` in a prompt explicitly labelled "Fiji time." For a booking stored as Fiji-noon-1-October (`"2026-10-01T00:00:00.000Z"` UTC), that slice produces `"2026-10-01T00:00"` — midnight — mislabelled as Fiji time in the very same prompt. Submitting that value **unchanged** then gets fed through `normalizePickupDatetime` (which correctly treats a naive value as Fiji wall-clock time), shifting the real booking **12 hours earlier** purely from an unedited resubmission.

**Fix:** new `fiji_time.js#toFijiWallClockInputValue(iso)` — the true inverse of `fijiWallClockToUtcIso`. Given a real UTC instant, it produces the naive `"YYYY-MM-DDTHH:MM"` string that actually represents that instant in Fiji local wall-clock time (via `Intl.DateTimeFormat(..., { timeZone: 'Pacific/Fiji', hour12: false })`, with a defensive `"24" → "00"` hour normalization for ICU builds that emit that at midnight). The change-form prompt now uses this instead of the raw slice. Verified end-to-end: an unedited resubmission through the actual UI path is now a genuine no-op, and the function round-trips correctly through `normalizePickupDatetime` for arbitrary instants, not just the one worked example.

**Tests:** the exact worked example (`toFijiWallClockInputValue('2026-10-01T00:00:00.000Z') === '2026-10-01T12:00'`, contrasted explicitly with the old buggy slice's output); a full end-to-end change-request submitting the actual prompt default unchanged, proving the booking's stored time is unaffected; a served-HTML check that the real script calls the new function and no longer contains the old raw-slice expression; the `.toString()`-splicing embedding regression (same mechanism/lesson as every other embedded function in this codebase); a round-trip property test across several arbitrary instants (not just the one worked example).

**Live verification (Playwright, `docs/screenshots/verify_round5.mjs`):** against the running demo server, a real booking stored as `2026-09-28T15:44:03.754Z` UTC — reading the raw stored value directly via the same API the guest app uses — shows the OLD buggy default would have been `"2026-09-28T15:44"`, while the ACTUAL prompt default is now `"2026-09-29T03:44"` (a full calendar day later, matching the pickup card's own displayed "3:44 AM Fiji time · Tuesday, Sep 29" — see `09-change-form-fiji-default-fixed.png`).
