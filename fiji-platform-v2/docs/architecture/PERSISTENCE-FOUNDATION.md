# Persistence and transaction foundation

## Layers and repository boundaries

`SqlDatabase` is the small D1-compatible port: execute, query, and atomic batch. `Persistence` translates adapter failures, supplies query-one/query-many/insert operations, and treats a zero-row conditional update as a conflict. `D1SqlDatabase` is the production adapter; tests use real in-memory SQLite.

Domain contracts remain separate and are owned by their corresponding engine packages: destination lookup, guest creation, immutable quotes, booking transitions, active drivers, dispatch acceptance, append-only wallet writes, and message enqueueing. They use domain values rather than SQL statements, do not share a generic CRUD repository, and do not yet implement Phase 1B engines.

## Transaction model

Booking state plus booking event plus audit, dispatch claim/offer/assignment plus event/audit, and wallet ledger plus idempotency/audit are assembled as parameterized statements and submitted as one atomic batch. Dispatch starts with a unique database claim whose trigger requires a live offer and an unassigned dispatching booking. A losing claim is a constraint failure, so the entire batch rolls back rather than checking affected rows after commit. Required audit writes are fail-closed in that boundary; optional telemetry, if introduced later, must not be called audit evidence.

## IDs and UTC time

UUID v4 is generated by Web Crypto through an injectable `IdGenerator`. Persisted time comes from an injectable `Clock`; `SystemClock` emits UTC ISO-8601 and `FakeClock` makes tests deterministic. Domain command code must not construct `Date` directly.

## Idempotency and audit

Mutation callers provide a key and operation scope and hash recursively key-sorted canonical JSON. A reservation ensures only one concurrent caller invokes the command factory; matching racers wait for and replay its stored safe result, while a mismatch is a stable conflict. New evidence, the mutation, and audit are committed together. Expiry is cleanup eligibility: evidence remains replayable until it is deleted.

Audit statements record actor, action, entity, before/after JSON, metadata, request context, and canonical time. Serialization happens before the batch. An audit failure aborts the command.

## Errors and command pipeline

Stable `ApplicationError` codes are the only public error vocabulary. The persistence boundary translates SQL/D1 detail to `DATABASE_ERROR`; safe response mapping suppresses causes and stacks. Commands follow HTTP parse → validation package → authorization → idempotency → domain command → transaction → audit → safe response. Transaction, idempotency evidence, and audit live inside the command's execute stage so no earlier layer can accidentally split the atomic boundary.
